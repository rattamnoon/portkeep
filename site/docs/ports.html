Local ports and on demand

Each tunnel owns one local port on your Mac while it runs. Portkeep checks that port before starting, lets several tunnels share it so one click switches environment, and can hold it open on demand until an app connects.

On this page

  1. Port conflicts
  2. Shared ports and switching environments
  3. On demand: start when an app connects

Port conflicts#

Before a tunnel starts, Portkeep checks that nothing is listening on 127.0.0.1 on its local port. If something is, the tunnel doesn’t start, and the row says which process holds the port, as lsof reports it:

Port 8123 is in use by clickhouse-server

From the row’s ⋯ menu you can then:

  • choose Use Port N: Portkeep picks a free port, trying your port + 10000 first and counting up (8123 becomes 18123), or from 20000 up when that would pass 65535. It saves the new port and starts the tunnel;
  • choose Change Local Port… and type one yourself;
  • or quit the program holding the port, then switch the tunnel off and on.

The editor warns you earlier: the Local port field shows In use when something already listens there. A port left in TIME_WAIT by a tunnel that was just stopped counts as free, so switching between tunnels on the same port doesn’t trip the check.

Shared ports and switching environments#

Two or more tunnels may use the same local port on purpose, such as Production MySQL and Development MySQL both on 3306. Only one runs at a time:

  • Switching one on switches the other off first, so changing environment is one click and your database client keeps the same address.
  • The editor shows Shared with Production MySQL next to the port, so you know.
  • When several are switched on together (a group switch, the master switch, portkeep start-group, or reopening at launch), one tunnel per port starts. If one of them already holds the port it keeps it; otherwise the first in the list wins. The others stay off.
  • Moving a running tunnel onto a port another running tunnel holds, by editing it, switches that other tunnel off.

The quick way to set this up: create the Production tunnel, choose Duplicate from its ⋯ menu, and change the copy’s name, group and host, keeping the port.

On demand: start when an app connects#

A tunnel you only use now and then doesn’t have to stay connected. Turn on Start when an app connects in the tunnel’s Advanced Options. Then, while the tunnel is switched on:

  1. Portkeep listens on 127.0.0.1 on the local port itself, and the row shows Standing by · starts when an app connects. No tool is running.
  2. When a client connects, Portkeep starts the real tunnel on a spare internal port and holds the client for up to 30 seconds until it is up. The row shows Connecting…, then Connected.
  3. Portkeep passes the connection through, and every later connection while it runs.
  4. When no connections have been open for Stop after minutes idle (default 10), Portkeep stops the tunnel and goes back to standing by. Set it to 0 to keep the tunnel running once it has started.

If the tunnel can’t connect within those 30 seconds, or stops on a failure, the waiting client’s connection is closed and the row shows the reason as usual. Standing by never counts as down, so it doesn’t notify you or put a dot on the menu bar icon.

Which tunnels can run on demand#

  • SSH local forwards and SOCKS proxies, AWS SSM, Kubernetes, Google Cloud IAP and Cloudflare Access: yes.
  • SSH remote forwards: no. Their port is on the server, so there is nothing on your Mac to listen on.
  • Custom commands: only when the command contains {port}, so Portkeep can move it to the internal port.

When the option isn’t available it is greyed out with Not available for remote forwarding, or for a command without {port}.

Limits#

  • On-demand tunnels pass plain TCP on 127.0.0.1 only.
  • An app that keeps a connection open, such as a database client with a connection pool, keeps the tunnel up: the idle time only counts while no connection is open.
  • Test Connection connects straight away rather than waiting for an app.
