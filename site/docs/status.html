Status and troubleshooting

Every tunnel shows one status line, in the menu and in Settings. This page explains each status, every failure message with its fix, how Portkeep retries, and where to find the log when you need more.

  2. Reconnecting

Statuses#

Status lineMeans
OffSwitched off. Nothing is running.
Connecting…Portkeep is checking the local port, starting the tool, or waiting for the local port to accept a connection.
Connected · 2h 14mThe local port accepts connections. The time is how long it has been up (just now for the first minute).
Standing by · starts when an app connectsAn on-demand tunnel: Portkeep holds the port and starts the tunnel when a client connects.
Reconnecting… can't reach bastionThe tunnel dropped or couldn’t start for a reason that can clear up on its own. Portkeep is waiting to try again. See Reconnecting.
Port 8123 is in use by clickhouse-serverAnother program holds the local port, so the tunnel can’t start. When Portkeep can’t tell which program, it says Port 8123 is in use.
A failure messageThe tunnel stopped on something you need to fix. It stays switched on but doesn’t retry. See Failures.

A tunnel is Connected only when a TCP connection to 127.0.0.1 on its local port succeeds; a running process isn’t enough. While connected, Portkeep checks the port every 10 seconds, and if two checks in a row fail it restarts the tunnel with Reconnecting… stopped responding. SSH remote forwards are the exception: they have no local port, so they count as connected while ssh keeps running.

A tunnel that is reconnecting, blocked by a taken port, or stopped on a failure puts a dot on the menu bar icon. Blocked and failed rows also show a warning triangle, and their ⋯ menu offers the fix.

Reconnecting#

These problems can clear up on their own, so Portkeep tries again:

Status lineCause
Reconnecting… can't reach <host>The tool reported that the host couldn’t be resolved or reached, the connection timed out, or it was refused.
Reconnecting… port didn't openThe tool kept running, but the local port didn’t accept a connection within 20 seconds.
Reconnecting… stopped respondingIt was connected, then two health checks in a row failed.
Reconnecting… exited (255)The tool exited with that status for a reason Portkeep doesn’t recognise. The log has its output.

The host in these messages is the SSH host, the AWS instance ID, the Kubernetes context, the IAP instance, the Cloudflare hostname, or “the server” for a custom command.

Waits between tries back off: 1, 2, 4, 8, 16, 30 and 60 seconds, then every 60 seconds for as long as the tunnel stays switched on. Once a tunnel has stayed connected for a minute, the next drop starts again from 1 second. Retry Now in the ⋯ menu skips the wait.

Sleep, wake and the network#

  • While the Mac is offline, a reconnecting tunnel waits without spending tries.
  • When the network comes back, every switched-on tunnel is restarted straight away, with the backoff reset.
  • When the Mac wakes from sleep, the same happens: Portkeep restarts every switched-on tunnel rather than waiting for the old connections to time out.

An on-demand tunnel goes back to standing by after a wake unless an app still has a connection open, in which case it starts again.

Failures and their fixes#

These need you, so Portkeep stops retrying, shows a warning, and (with notifications on) tells you once. After fixing the cause, choose the fix or Retry Now in the row’s ⋯ menu, or switch the tunnel off and on.

Host key changed#

Host key changed for bastion. Check it, then remove the old key from known_hosts.

ssh refused to connect because the server’s key doesn’t match the one in ~/.ssh/known_hosts. That can mean the server was rebuilt, or that something is intercepting the connection. Confirm the new key with whoever runs the server, then remove the old one and connect once in Terminal to accept the new key:

ssh-keygen -R bastion
ssh bastion

Key refused#

bastion refused the key. Add it to the agent with ssh-add --apple-use-keychain.

The server answered Permission denied. Portkeep runs ssh with BatchMode=yes, so it can’t ask for a password or passphrase. Load the key into the agent and the macOS keychain, or set an identity file that doesn’t need a passphrase:

ssh-add --apple-use-keychain ~/.ssh/id_ed25519

Check that ssh bastion in Terminal logs in without prompting.

AWS sign-in expired#

AWS sign-in expired for profile prod.

The AWS CLI said the profile’s SSO token has expired. Choose Sign In to AWS… in the ⋯ menu, which runs aws sso login --profile prod and opens your browser, or run it yourself in Terminal and then switch the tunnel off and on.

Session Manager plugin missing#

session-manager-plugin is not installed.

The AWS CLI couldn’t find the Session Manager plugin. Install it, and check Settings › Tools shows it with a ✓:

brew install --cask session-manager-plugin

Forward refused#

The server refused the forward.

The SSH server wouldn’t open the forward (administratively prohibited, or a remote port forward that failed). The server may not allow forwarding (AllowTcpForwarding), or for a remote forward, the port on the server may be taken. Ask the server’s admin, or pick another port.

Port in use#

Port 8123 is in use by clickhouse-server

Before starting, Portkeep checks that nothing listens on 127.0.0.1 on the local port. If something does, it names the process and doesn’t start. Choose Use Port 18123 (the number varies) in the ⋯ menu to move the tunnel to a free port, use Change Local Port… to choose one, or quit the other program and switch the tunnel off and on. A tool that itself reports address already in use lands here too. See Port conflicts.

Tool not found#

kubectl not found. Install it with brew install kubectl.

Portkeep couldn’t find the tool on your login shell’s PATH. Install it with the command shown, or if it lives somewhere else, set its path in Settings › Tools. The install commands are:

ToolInstall with
sshbrew install openssh (macOS includes one)
awsbrew install awscli
session-manager-pluginbrew install --cask session-manager-plugin
kubectlbrew install kubectl
gcloudbrew install --cask google-cloud-sdk
cloudflaredbrew install cloudflared

Other messages#

Exited (-1). See log. means the tool couldn’t be started at all, for example because a path set in Settings › Tools isn’t an executable file. The log has a “Could not start …” line with the reason.

Portkeep recognises failures by the text the tool prints, so a message in another language, or from a custom command, may come through as an exit status. The log always has the original.

Logs#

Show Log (in a row’s ⋯ menu, or on the tunnel’s page in Settings) opens a window titled “<name> — Log” with the last 500 lines the tool printed, standard output and error together, updated every second. You can select and copy the text. Portkeep adds a few lines of its own, such as when an on-demand tunnel starts listening or stops after being idle.

The log is kept in memory only: it starts empty when Portkeep launches and isn’t written to disk. When you report a bug, include the lines around the failure, with host names and account IDs removed.

Notifications#

With Notify when a tunnel drops on in Settings › General (the default), macOS notifies you:

  • “<name> is down” when a switched-on tunnel has not been connected for 30 seconds, with its current status;
  • “<name> needs attention” straight away when it stops on a failure or a taken port;
  • “<name> is back”, “Connected on 127.0.0.1:<port>.”, when it connects again after either.

Each tunnel gets at most one notification per change, so a tunnel retrying for an hour says so once, and “is back” replaces “is down” in Notification Center. Switching a tunnel off, or an on-demand tunnel standing by, never notifies. macOS asks for permission the first time a notification would be sent.
